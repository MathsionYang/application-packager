# 压缩耗时与第三方依赖子包方案

分析日期：2026-10-14。依据：当前 Qt 打包代码、用户正在构建的 child-C 脚本及日志、ISCC 进程只读采样、Inno 官方文档。本轮仅分析，不修改程序或发行包，不运行安装器。

## 1. 结论

可以把不经常变化的第三方依赖做成独立子安装包。**真正减少后续耗时的条件是：依赖子包预先生成并持久复用，依赖未变时不再编译；总包不再压缩这些已压缩子包。** 只拆包、每次仍重新编译全部子包，不能消除主要压缩工作。

当前慢的位置是 C 子安装器，尚未进入总包编译。因此，关闭外层重复压缩可以减少后续工作，但不能单独解决当前 child-C 的长时间 Compressing。当前子包使用 `Compression=lzma2`，实际等级是 `lzma2/max`，也未开启多个压缩块并行，是需要优先比较的参数。

推荐方向：完整依赖目录单独生成并复用；C 主程序只封装经常变化的文件；总包直接嵌入已有子包。首次构建仍需要压缩依赖，后续未变时跳过。

| DLL | 1,019 个 |

2.9 万是所有文件的数量，不能称为 2.9 万个 DLL。DLL 体积、全部文件的总字节数尚未测量，不能仅凭文件数量确认耗时占比，也不能证明存在可安全删除的重复 DLL。

已有构建记录显示，新版从索引 C 到开始子编译约 4 秒；当前脚本所有 Source 均直接引用原目录，旧的整目录快照阶段已经去掉。剩余长耗时发生在 ISCC 的压缩工作中。

## 3. 三种处理方式的区别

| 方式 | 首次构建 | 后续仅主程序变化 | 局限 |
| --- | --- | --- | --- |
| 仅把 DLL 分成另一个子包，每次全部重建 | 仍压缩全部依赖 | 仍压缩全部依赖 | 主要耗时仍在，且机械拆 DLL 可能破坏运行 |
| 依赖子包预构建/缓存复用 | 需要压缩依赖一次 | 跳过依赖压缩，只构建主程序并封装 | 需要可靠的版本、目录、缓存失效和卸载规则 |
| 完全不压缩 | 减少压缩计算 | 同样减少压缩计算 | 安装包可能明显增大，读取和写出文件仍需时间 |

保留一个统一安装包交付没有障碍。建议结构为：

```mermaid
flowchart LR
    U[统一安装包] --> R[已有运行环境包]
    R --> D[C 第三方依赖子包：预构建并复用]
    D --> C[C 主程序子包：按本次版本构建]
```

A/B 继续沿用各自独立的软件子包及选择规则。C 为必装软件时，其依赖应随 C 安装，而不让用户自行决定是否缺少必需依赖。

## 4. 怎样拆分才可运行

不建议仅把 `*.dll` 抽到一个平铺目录。当前载荷包含 Python 原生扩展、Python 模块、包数据和可能关联的 CUDA 资源；DLL 也可能依赖同目录下其他文件及既有搜索路径。

应按可部署的完整依赖目录或模块分组，保持原相对目录。例如将稳定的 `Gravity/lib/...` 依赖目录作为候选，并单独核对发布根目录及 lightglue 内部依赖。主程序、配置、模型和插件是否也位于这些目录，必须先核对，不能把整个 Gravity 不加区分地认定为第三方依赖。

还需明确以下规则：

- 依赖包与 C 主包安装到兼容的目标目录，保持 DLL/Python 模块的相对路径，不向系统目录随意复制私有 DLL。
- 主包与依赖包的文件集合互不重复，避免升级或卸载时互相覆盖、误删。
- 依赖包具有稳定标识，记录版本、架构及与 C 的兼容范围。同一安装目录下要区分卸载文件位置。
- 明确依赖是否单独卸载。若要求卸载 C 时一并移除私有依赖，需要协调卸载；共享依赖不能随某个应用自动删除。
- 依赖升级、降级和旧版本覆盖必须有规则；不能仅因某个文件存在便判定依赖可用。

## 5. 依赖包复用策略

两种可行入口：

1. **手动预构建**：先生成指定版本的依赖安装包，日常构建选择这个已有安装包。现有工具支持添加 EXE 环境包，但依赖包本身仍须正确处理 C 目标目录与版本；不能直接拿任意 DLL 压缩文件当环境安装器。
2. **自动缓存**：工具第一次生成依赖子安装器后保存在持久目录；后续检查依赖配置及文件索引，命中则直接复用。缓存不能存于每次清理的 `.build-*` 任务目录。

自动缓存应记录依赖分组、版本、架构、相对文件清单、源元数据、压缩参数、编译器及缓存产物校验值。依赖增删改、目标规则或压缩策略变化时重建，并提供“强制重建依赖”的操作。

延续当前快速模式时，可以使用大小、时间戳等元数据作为缓存判断依据，避免每次通读全部大型依赖；但这不能保证检测到保留元数据的内容修改。需要严格内容一致性时，应使用可信发布校验清单或额外内容校验，并接受对应读取成本。不能把快速缓存声明为逐字节验证。

即使命中缓存，统一 EXE 仍需要读取并写入依赖子包；交付的统一安装包仍包含全部依赖，不能把缓存复用理解为最终包体不再包含这些文件。

## 6. 可同时使用的压缩优化

### 6.1 总包不再重复压缩

当前子安装器已经采用 LZMA2。外层再次压缩通常收益有限，但要再次扫描和计算。可选：

```ini
; 总安装包只封装已有子安装器和环境包
Compression=none
SolidCompression=no
```

若外层还需要压缩其他普通文件，则只对已压缩载荷使用：

```ini
Flags: dontcopy nocompression
```

`dontcopy` 只表示由脚本提取、跳过常规复制阶段，不表示不压缩；`nocompression` 才会阻止编译器尝试压缩该文件。不要添加 `external`，否则会改变独立交付方式。不能将全部 DLL 或 EXE 一概认定为已压缩文件。

### 6.2 降低子包等级，并使用多块并行

本机可优先对以下候选做实际目录比较：

```ini
; 均衡候选
Compression=lzma2/normal
SolidCompression=yes
LZMANumBlockThreads=4
```

`lzma2` 未写等级时默认 max；块线程默认 1。normal/max 默认每个块可使用两个匹配查找线程，所以在本机 8 核上，4 块线程是合理候选，但不是已实测的最优参数。块并行可能降低压缩率，实际收益取决于数据量、块大小及其他资源使用。

速度更优先时，可比较：

```ini
Compression=zip/1
SolidCompression=no
```

`lzma2/fast` 也有效，但其默认字典只有 32 KiB，包体可能明显增大。ZIP 支持 `zip/1` 至 `zip/9`，不存在 `zip/fast`。关闭 SolidCompression 不能单独保证编译更快；它还影响压缩率和安装时的随机提取能力。

### 6.3 精简发布内容

当前有大量头文件和测试目录，值得在应用依赖分析之后评估。纯运行场景可能不需要部分开发头文件或测试资源，但 torch 扩展、运行时编译、动态导入等功能可能使用它们。只能按确认过的排除清单处理，并验证真实应用；不能直接删除全部 `.h`、tests、`.pyi` 或同名 DLL。

### 6.4 后续才考虑的项目

独立 A/B/C 子包可以考虑并行构建或分别缓存，但应与压缩线程共同限制并发，避免多个多线程压缩器争抢 CPU、内存和磁盘。当前只有 C 慢时，并行其他角色不能缩短 C 自身的关键路径。

## 7. 建议优先级和验证方式

1. 先降低 C 子包压缩级别并比较 4 块线程；同时关闭总包对已压缩载荷的重复压缩。
2. 对长期重复构建，确定完整依赖分组，生成并持久复用依赖子包；主程序包排除这些已归属依赖包的文件。
3. 再评估头文件、测试资源及确认重复项的发布精简。

后续应在同一份稳定发布目录上记录：索引时间、各子包压缩时间、总包封装时间、最终体积、CPU 峰值及内存，再测试安装后启动、升级和卸载。依赖缓存应比较首次构建与第二次命中缓存的时间，而不只比较首次。

本轮没有运行基准编译，以免与用户正在执行的 ISCC 争抢资源；没有精确加速倍数或体积增长实测。本轮程序源码、EXE 和 ZIP 保持现状。
