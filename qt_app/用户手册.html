安装包工坊
用户操作手册

从选择已编译的软件目录，到生成一个包含多个独立软件和运行环境的安装包。本手册按照实际界面说明每一步，也覆盖 DLL 缓存复用、自动版本、安装路径和独立卸载。

开始第一次打包 →遇到问题，查看排查方法
适用：原生 Qt 桌面版更新：2026 年 10 月 15 日图片、样式已内嵌，无需联网
C 必填，A / B 可选

三套软件独立安装、独立运行、独立卸载。

多个运行环境

支持选择 VC 等已有 EXE / MSI 安装包。

重复打包可复用 DLL

人工选择依赖，通过哈希决定复用或重建。

01

第一次打包：按这六步操作

首次使用可以先只打包软件 C。A、B、环境包及 DLL 缓存都可以按实际需要逐步加入。

  1. 打开程序并配置 Inno Setup

    运行 DesktopPackager.exe，进入左侧 工具设置，选择真实的 ISCC.exe，点击 保存设置。左下角应显示“编译器可用”。详细步骤 →

  2. 选择功能软件 C 的发布目录

    进入 打包工作台，在 C 行点击 浏览 → 选择完整发布目录。该目录应包含主程序及其运行所需的全部文件。需要 A / B 时再填写对应行。如何选择入口 →

  3. 按需加入已有环境安装包

    点击 添加安装包，可一次多选多个 EXE / MSI。用上、下箭头调整环境安装顺序，展开 安装参数 核对参数。参数示例 →

  4. 选择独立的输出目录

    在 安装包输出 中填写输出目录；需要自定义图标时选择外置 ICO。展开 更多打包选项 设置名称，保留“自动使用软件 C 的主程序版本”勾选。输出与版本 →

  5. 点击“开始打包”

    如果弹出主入口选择框，选中真正用于启动软件的 EXE。观察 打包日志；等待“打包完成”，不要在构建期间修改源目录。查看构建结果 →

  6. 验证并交付生成的 Bundle.exe

    在构建详情点击 打开输出目录，找到本次生成的 …-Bundle.exe。先在测试机验证安装、启动、升级和卸载，再交付使用。安装操作 →

首次不必配置 DLL 缓存。不勾选依赖 DLL 时，全部文件仍会进入正常主软件安装包。以后需要加快重复打包时，再使用第 06 章。
02

准备文件与目录

先分清三种路径

路径在哪里填写作用与示例
软件发布目录工坊 → 软件发布目录待打包的主程序及依赖，例如 D:\PackagerWork\Releases\C。
安装包输出目录工坊 → 安装包输出保存生成的安装包与构建记录，例如 D:\PackagerWork\Output。
目标安装根目录运行生成的安装包时选择最终用户把 A / B / C 安装到哪里，例如 D:\Apps。不是打包输出位置。

建议的文件组织

示例结构，可按实际磁盘调整
D:\PackagerWork\
├─ Releases\
│  ├─ C\                  功能软件 C 的完整发布目录
│  │  ├─ FeatureApp.exe
│  │  ├─ vendor.dll
│  │  └─ resources\
│  ├─ A\                  认证软件 A，可选
│  └─ B\                  引擎软件 B，可选
├─ Prerequisites\          已有运行环境安装包
│  ├─ vc_redist.x64.exe
│  └─ other-runtime.msi
├─ Branding\setup.ico      自定义安装包图标，可选
├─ Records\                配置及依赖记录
└─ Output\                 生成的安装包与构建记录
  • A / B / C 的来源目录必须各自独立，不能相同或互相包含。
  • 输出目录不能与任一软件来源目录相同或互相包含。不要把输出目录设为上面的 D:\PackagerWork 总目录。
  • 使用真实的普通目录和文件；软件目录中的符号链接、目录联接等重解析点不受支持。
  • 主程序、DLL、资源文件、配置模板等应已经编译并整理好。选取干净的发布目录，避免把源代码、旧安装包、调试文件或个人数据一起打包。

打包电脑与目标电脑分别需要什么

执行打包的电脑

使用 Windows 桌面环境，保留完整的 DesktopPackager 文件夹及 _internal，并安装 Inno Setup 7。运行已构建的工坊程序无需另外安装 Python。

运行安装包的目标电脑

无需安装 Inno Setup、Python 或工坊本身。业务软件所需的 VC 等运行环境由你加入的环境安装包提供；运行安装包时会请求管理员权限。

原软件安装器与发布主程序用途不同。这里的 A / B / C 应提供“主程序和依赖文件所在目录”，不能选一个现有软件安装器并期待工坊自动解包它。已有 VC 等安装器应添加在“运行环境安装包”区域。
03

配置打包引擎

设置 ISCC.exe

  1. 点击左侧 工具设置。
  2. 在 ISCC.exe 路径 行点击 浏览，选择 Inno Setup 的命令行编译器。
  3. 本机默认位置为 D:\PCAPP\Inno Setup 7\ISCC.exe。安装在其他位置时，选择实际路径。
  4. 点击 保存设置，确认出现“已保存”，左下角显示“编译器可用”。
  5. 回到 打包工作台。
选择路径后要点击“保存设置”。“恢复默认路径”只把输入框恢复为默认位置；如果默认位置并不存在，仍需重新选择真实编译器。Inno 安装目录还应包含 Languages\ChineseSimplified.isl。

设置哈希线程数

哈希线程数 允许 1–8，默认 2。它控制人工勾选 DLL 的 SHA-256 校验并发，不等于同时安装软件的数量，也不是压缩速度档位。

一般先保留 2；SSD 可尝试 2–4，磁盘繁忙或机械硬盘可尝试 1–2，结合实际日志耗时选择。增加线程数不保证总打包时间同比缩短。

04

选择软件 A / B / C

软件是否必填生成安装包后的行为
功能软件 C必填必装组件，用户不能取消勾选。
认证软件 A可选填写来源后，进入总安装包；最终用户勾选时才安装。
引擎软件 B可选填写来源后，进入总安装包；最终用户勾选时才安装。

方式一：选择完整发布目录

在对应软件行点击 浏览 → 选择完整发布目录，选择包含主程序、依赖和资源的目录。也可以直接在输入框填写完整路径。

点击“开始打包”后，程序先寻找目录顶层的 EXE；只有顶层没有 EXE 时，才向子目录寻找。找到多个候选时，会弹出主入口选择框。选择真正启动该软件的 EXE，相对路径会保存在配置中。

方式二：选择主程序 EXE

点击 浏览 → 选择主程序 EXE，选择业务主程序。程序把它作为入口，并打包这个 EXE 所在目录的全部文件和子目录。

主 EXE 在 bin 子目录时要特别注意。如果文件位于 Release\bin\Main.exe，直接选择这个 EXE 的范围是 Release\bin，不会包含旁边的 Release\resources。需要父目录其他资源时，应选择完整 Release 目录，并在入口选择框中选择正确主程序。

加入、移除或更换 A / B

A / B 留空即可不包含该软件；已填写时，可点击路径行的清空图标移除。改变软件来源路径后，已保存的主入口会被清除，下一次打包会重新判断入口；同时请复核该软件原来勾选的 DLL 相对路径是否仍然有效。

右侧 本次打包 汇总包含的软件和交付文件预览。“已配置”“配置就绪”是表单状态提示，正式路径、入口、图标及文件校验仍在点击“开始打包”后执行。

05

添加多个运行环境安装包

添加与排序

  1. 在 运行环境安装包 区域点击 添加安装包；空列表也可点击 添加环境。
  2. 选择已有的 .exe 或 .msi。文件选择框支持 Ctrl / Shift 多选，可一次加入多个安装包。
  3. 用每行右侧的上、下箭头调整顺序；用删除图标移除不需要的环境。重复加入同一路径会被忽略。
  4. 展开每一行的 安装参数，确认静默安装和禁止自动重启参数。

安装参数如何填写

环境安装器程序提供的起始参数操作要求
MSI/qn /norestart根据供应商文档补充所需属性，工坊还会为 MSI 流程附加禁止重启和日志参数。
标准命名的 VC 安装器/install /quiet /norestart适用于文件名为 vc_redist.x64.exe、vc_redist.x86.exe 或 vc_redist.arm64.exe（不区分大小写）的情况。
其他 EXE默认留空查阅对应安装器文档后填写；重命名后的 VC 安装器也应手工确认参数。
EXE 没有通用静默参数。/S、/silent、/quiet 不能互相替代。参数应为单行文本；是否支持禁止重启也由安装器自身决定。选择对应业务软件所需架构的环境包，不能只按打包电脑架构判断。

安装顺序、失败与取消

第一阶段按列表顺序执行全部环境包
→
第二阶段安装必装软件 C
→
第三阶段安装用户勾选的 A / B
  • 环境包自身失败或在其窗口取消：总包记录警告，继续后面的环境包与业务软件。
  • A / B / C 子安装器失败：停止后续软件；已经安装完成的软件保留，不进行整体回滚。
  • 点击总安装器的取消按钮：会等待当前子安装器退出，然后停止后续任务。这与取消某一个环境包不同。
  • 需要重启的常见成功码 3010 会记录为手动重启需求；工坊生成的安装流程不主动要求自动重启，第三方 EXE 仍需使用供应商支持的参数控制。
06

DLL 依赖、哈希记录与缓存复用

适合大型软件里有一批长期不修改的第三方 DLL，而自己的 EXE 或少量文件经常更新的场景。首次仍要哈希和压缩；后续内容一致时可以复用依赖子包。

勾选 DLL 是“分组缓存”，不是“排除文件”。勾选的 DLL 放入可复用依赖子包；其他文件仍放入主软件包。最终安装包包含完整软件。

第一次：人工选择依赖 DLL

  1. 先选择软件来源，再点击该软件行的 依赖文件。
  2. 等待扫描完成。列表显示所有文件，但只有 DLL 可以勾选。
  3. 通过 搜索相对路径、仅 DLL、大小筛选定位第三方文件。
  4. 直接勾选文件前的复选框；或先多选行，再点击 勾选所选行。点击 全选筛选结果 可勾选当前筛选范围内的可用 DLL。
  5. 按需点击 保存记录，选择源目录之外的 JSON 保存位置，等待所选 DLL 校验完成。
  6. 最后点击 使用选择，把本次选择和记录路径应用回主界面。

行被高亮不等于已勾选；筛选隐藏的已勾选文件仍然保留。用 仅已选 检查最终名单，选中需要取消的行并点击 取消所选行。只点“关闭”不会应用本次未确认的选择。

理解两种依赖记录

记录类型保存结果适合用途
选择记录一个 JSON，记录 DLL 相对路径、大小和 SHA-256恢复人工选择；尚无匹配的已生成依赖包时使用。
可复用包记录JSON + 同名 .files 文件夹携带已经生成的依赖 EXE，方便备份或迁移；前提是存在匹配的成功构建记录，且当前 DLL 校验一致。

成功打包后，重新打开对应软件的“依赖文件”窗口，再点击“保存记录”。如果当前所选 DLL 与已有依赖包匹配，会导出 JSON 及同名 .files 文件夹；里面按缓存键和代次保存依赖 EXE。

Records\
├─ C-依赖记录.json
└─ C-依赖记录.files\
   └─ <缓存键>\<代次>\dependencies.exe
移动记录时要一起复制。JSON 与整个同名 .files 文件夹应保持相对位置。选择记录不携带依赖 EXE；成功构建目录中的依赖 JSON 也不等于已经导出了可携带的 .files。

下一次打包：导入记录并比较哈希

  1. 选择本次软件发布目录，打开对应角色的 依赖文件 窗口。
  2. 点击 导入记录，选择同一角色的 JSON。C 的记录用于 C，A / B 同理。
  3. 检查已选 DLL，确认列表没有“缺失”项。导入记录不会自动切换源目录，也不会立即重新哈希；界面会显示“已导入 · 待校验”。
  4. 点击 使用选择，回到工作台后开始打包。
  5. 正式构建会重新计算所选 DLL 的 SHA-256，验证已有依赖包后，决定复用或重建。

什么时候复用，什么时候重建

  • 复用：所选 DLL 的相对路径和内容、产品身份、架构、打包规则及编译工具链等一致，缓存 EXE 也通过校验。
  • 重建：任一所选 DLL 修改、改名、选择范围改变，或依赖包缺失 / 损坏、规则 / 工具链变化。当前会重建该软件整组所选 DLL 的依赖子包。
  • 未选文件变化：通常只影响本次主软件包；在依赖缓存条件仍一致时，依赖子包可以继续复用。

默认缓存位置为 %LOCALAPPDATA%\DesktopPackager\cache\dependencies。每次构建仍要索引软件文件、读取并哈希所选 DLL、生成主包与总包；缓存命中不等于完全跳过磁盘读写。源目录直接用于编译，不再复制完整软件目录到临时快照。

缺失 DLL 要先处理。更换源目录后，原有相对路径选择会保留。出现“缺失”时，补齐对应 DLL，或明确取消该项再使用选择；不能把缺失依赖静默忽略。记录及伴随目录必须保存到发布源目录之外。
07

输出、图标与自动版本

设置输出目录与图标

在 安装包输出 中点击“输出目录”行的 浏览，或直接填写可写目录。图标可选，点击“安装包图标（可选）”行的浏览选择 .ico；清空则使用 Inno Setup 默认安装器图标。

ICO 必须可读取，并放在所有软件源目录和输出目录之外。这个图标用于总安装包 EXE，不改变业务主程序及其快捷方式本身的图标。

自动跟随软件 C 的版本

  1. 展开 更多打包选项。
  2. 设置 安装包名称，例如“桌面软件套装”。
  3. 保留默认勾选 自动使用软件 C 的主程序版本。此时“版本号”为只读状态。
  4. 点击开始打包，确定 C 的主入口后，程序读取主 EXE 版本并更新表单；正式构建还会再次读取，以本次实际解析值生成总包。
优先读取C 的合法 ProductVersion
→
无可用值时C 的合法 FileVersion
→
都不可用时使用 1.0.0，并写日志

例如 C 的 EXE 版本从 2.3.0 更新为 2.4.0，重新打包后的套装版本自动变为 2.4.0，同步体现在总安装器、实际输出文件名和保存的构建配置中。不会在每次打包时自动“加 1”；EXE 版本没变，套装版本也不因重新打包而自行增加。

需要手动指定套装版本时，取消该复选框，再填写例如 1.0.0、2.1.3.4 的版本号。A / B / C 各自子软件版本仍从各自主 EXE 读取；套装名称和版本不是同时重命名三套软件。

选择目录后，表单可能暂时显示上次版本。自动版本在开始打包并确定 C 入口时刷新；请以本次构建日志、详情和实际输出文件为准。要发布新版本，应先更新并重新编译 C 的 EXE 版本资源。

桌面快捷方式

创建各软件独立的桌面快捷方式 默认勾选。取消后不生成桌面快捷方式，开始菜单中的软件入口与卸载入口仍由各子安装器管理。

08

开始构建与查看结果

点击开始前检查

  • C 已选择完整、可运行的发布内容；A / B 只填写需要加入的产品。
  • 编译器已保存，输出目录独立且可写。
  • 每个环境包的架构、参数和顺序已确认。
  • 依赖选择已点“使用选择”，没有缺失 DLL。
  • 自动版本模式与本次发布要求一致，图标路径符合规则。
  • 打包期间暂停修改、重新编译、同步或覆盖发布目录。

日志与进度怎么读

点击底部 开始打包 →。程序后台校验配置；多个候选主入口时，按提示选中正确 EXE。之后会依次进行文件索引、DLL 哈希 / 复用或重建、软件子安装器编译、源目录变化检查、环境包校验、总包编译及最终发布。

打包日志 会显示实际编译器输出。看到 Compressing 表示正在压缩，耗时与文件大小、数量、磁盘和 CPU 有关；界面的阶段百分比不是准确剩余时间。没有新的日志行也不必立即认定程序卡死。

取消当前构建

点击 取消打包，等待“正在取消…”结束。程序会停止当前编译进程并清理本次临时任务；不会把尚未完成的 EXE 当作可交付结果，也不会激活失败 / 取消任务的新缓存基线。构建期间关闭主窗口，会提示是否取消当前构建并安全退出。

成功后找到哪一个文件

成功后会显示构建详情，点击 打开输出目录。实际文件名包含构建时间与随机 ID，避免覆盖旧产物；右侧工作台的预览是简化名称。

Output\
├─ 桌面软件套装-2.4.0-20261015-143000-a1b2c3d4e5-Bundle.exe
└─ build-20261015-143000-a1b2c3d4e5\

交付给最终用户的是本次生成的 Bundle.exe。它包含完整安装载荷，可以单独交付。旁边 build-… 是排查、配置和记录证据；里面的脚本可能引用源目录或已清理的临时路径，不应直接当作可无条件重跑的独立构建工程。

失败时先看工作台日志和“构建记录 → 查看详情”。部分失败会在输出目录留下 build-… 诊断文件，但预校验失败可能还没有创建该目录。

09

在目标电脑安装

下面操作的是工坊生成的 Bundle.exe 安装向导，和工坊本身的“输出目录”设置不同。

  1. 运行总安装包

    将 Bundle.exe 复制到目标电脑后双击；按 Windows 提示允许管理员权限。

  2. 选择业务软件组件

    C 是必装组件。总包中包含 A / B 时，可按需要勾选；没有加入总包的产品不会凭空出现。

  3. 选择安装根目录

    在“选择安装位置”页选择根目录，例如 D:\Apps。程序在其下为每个产品生成独立子目录。最终产品目录过长时会提示换更短的根目录。

  4. 检查安装摘要并开始

    摘要列出将执行的环境包与所选软件、实际产品安装路径。确认后开始；环境包优先，随后业务软件分别安装。

  5. 查看结果并启动软件

    结束页显示结果与日志位置。按需手动重启；通过各自桌面或开始菜单入口启动 C / A / B，验证功能和运行环境。

D:\Apps\
├─ FeatureApp-C-A1B2C3D4\
├─ AuthApp-A-E5F60718\     勾选 A 时才安装
└─ EngineApp-B-192A3B4C\   勾选 B 时才安装

以上是结构示例。实际子目录由产品名称、角色和产品 ID 短段生成，不固定叫 Product-C。A / B / C 独立运行；总包只是安装编排，不会替业务软件新增认证、启动或进程依赖关系。

日志位置会在安装向导中显示，通常位于 %LOCALAPPDATA%\DesktopPackager\InstallLogs\<本次时间>。环境安装器失败被跳过后，业务软件是否能正常启动还取决于目标电脑已具备哪些运行环境。

升级、产品 ID 与独立卸载

产品 ID 自动生成并沿用

首次打包时，工坊为每个产品自动生成安装身份 AppId，并保存到应用数据目录的 products.json。后续同一产品继续沿用该身份；版本号变化不会重新生成产品 ID。

身份识别与软件角色、主 EXE 文件名和产品名称有关；改变这些信息可能被视为新产品。只改变套装版本、来源所在磁盘路径、输出目录或本次是否包含其他软件，不应当据此创建新的产品身份。

更新一个已有产品

  1. 使用同一份工坊应用数据，保留原 products.json。
  2. 准备新发布目录，先更新业务 EXE 版本资源。自动模式下套装版本会跟随 C；A / B 自己的版本读取各自 EXE。
  3. 恢复已有配置和 DLL 选择，检查路径，重新打包。
  4. 在目标电脑运行新版总包。已安装产品默认沿用注册表中的原安装位置；原地升级建议沿用这个位置。
  5. 验证更新后的软件功能、配置和卸载入口。
修改安装根目录不是迁移旧软件。它只改变本次安装位置，不自动迁移或清理旧目录。改目录后 Windows 卸载项指向新位置，不要再使用旧目录中的卸载程序。升级中可识别的用户配置和数据按现有保留规则处理，实际业务数据仍应按软件自身要求备份。

三种卸载入口

  • Windows 设置：进入“应用 / 已安装的应用”（或“应用和功能”），找到对应软件，选择卸载。
  • 开始菜单：打开该软件独立分组，选择“卸载 …”。
  • 安装目录：运行该产品目录里的 unins*.exe 卸载程序，常见为 unins000.exe。

A / B / C 各自有卸载记录，卸载其中一个不等于卸载另外两个。总安装器不额外生成一个“整套软件卸载”入口。VC 等共享运行环境由供应商安装器注册和管理，卸载业务软件时不会由总包统一卸载共享运行库。

11

保存配置、复用历史与备份

保存配置与导入配置

表单修改会自动保存到当前应用数据目录；重启后继续加载。底部 保存配置 是把当前配置额外导出为 JSON，适合按项目备份；导入配置 会替换当前表单并保存。

配置保存软件路径、入口、运行环境参数、输出位置、图标、自动版本选项及 DLL 选择等。导入配置不自动打包，也不代表其中的路径已通过校验；换电脑后先检查文件实际位置。导入文件上限为 1 MB。

导入旧配置或使用旧构建记录时，如果其中没有自动版本选项，程序默认开启自动版本。原先手填的版本会在开始打包时由 C 主程序版本替换；需要继续使用手填版本时，请先取消“自动使用软件 C 的主程序版本”，再核对版本号。

使用构建记录

  1. 点击左侧 构建记录，查看最近 30 条成功、失败或取消记录。
  2. 点击 查看详情，读取输出位置、配置、日志和失败原因。
  3. 点击 使用此配置，返回工作台并恢复该次配置；检查后再手动点击“开始打包”。
  4. 输出 EXE 仍存在时，详情提供 打开输出目录。

迁移电脑或备份项目

备份内容作用
软件发布目录、环境包与 ICO真实输入文件。配置 JSON 只保存引用路径，不携带这些文件。
导出的工坊配置 JSON恢复界面填写内容、运行环境顺序及选项。
依赖 JSON + 同名 .files 目录恢复人工 DLL 选择，并携带匹配的依赖子包。
应用数据中的 products.json沿用原产品安装身份，是继续升级已有软件时的重要备份。
本次 Bundle.exe 与 build-* 记录保存已交付安装包，以及对应配置、清单和日志证据。

默认应用数据目录为 %LOCALAPPDATA%\DesktopPackager，包含 config.json、history.json、products.json 和依赖缓存。配置 JSON 导入不会导入 products.json；迁移时先关闭工坊，备份并恢复该文件到实际使用的数据目录，然后启动并导入配置。界面没有单独的产品 ID 导入按钮。

如果使用了启动参数 --data-dir，配置、身份和缓存会随该数据目录改变。损坏的 config / history 文件会保留为 .corrupt-… 后回退；产品身份文件损坏则会停止构建，需恢复有效备份。

常见问题与排查

点击问题展开说明，打印时会自动展开全部。

必须安装 Inno Setup 吗？

执行打包的电脑需要安装 Inno Setup 并配置 ISCC.exe。运行最终生成的 Bundle.exe 的目标电脑不需要安装 Inno Setup。

我只想填路径快速打包，DLL 依赖这一步能跳过吗？

可以。不选择任何 DLL 时，完整软件内容仍进入主软件安装包。DLL 选择用于减少后续重复压缩，适合有稳定大型依赖的项目，不是完成第一次打包的必要条件。

“索引软件 C”和 Compressing 仍然耗时，为什么？

程序直接读取来源目录，仍需遍历文件并生成主包。Compressing 是 Inno 的压缩阶段。DLL 缓存首次需要建立；命中后仍会校验所选 DLL 与缓存包，未缓存的文件和总包仍需生成。先确认日志有“复用依赖子包”，再结合文件数量、磁盘和 CPU 判断耗时；哈希线程数只影响选中 DLL 的校验。

导入记录后为什么还要哈希？

旧记录只能证明上次记录的内容。程序在本次正式构建中重新计算所选 DLL 的 SHA-256，避免文件已修改却错误复用旧依赖包。导入时“待校验”是正常状态。

自动版本一直是 1.0.0，或者没有随打包次数增加？

自动版本跟随 C 主 EXE 的版本资源，不按打包次数递增。确认选择的 C 主入口正确，并在 Windows 文件属性“详细信息”中检查产品版本 / 文件版本。两个字段都无可用值时使用 1.0.0，日志会说明来源。准备新版本时先更新 EXE 版本资源并重新编译；需要单独套装版本时取消自动选项。

产品 ID 为什么没有每次重新生成？

同一产品需要沿用 AppId，Windows 才能把新包作为已有产品的更新管理。首次自动生成，以后沿用。主程序名称、产品名称或角色发生变化可能建立新身份；迁移电脑时要保留 products.json，而不只是导入表单配置。

VC 安装失败或取消后，为什么仍继续装业务软件？

这是当前设计。环境包被视为允许失败的前置步骤，失败记入日志后继续。业务软件启动仍可能依赖该环境，请在目标机核对运行库是否已安装；如果点击的是总安装器的取消按钮，则会停止后续任务。

安装后在哪里卸载？为什么看不到总套装的卸载项？

请查找 A / B / C 对应的独立产品名称，也可从各自开始菜单“卸载 …”或安装目录 unins*.exe 卸载。总包仅编排安装，不注册伞形卸载项。要完整移除三套软件，分别卸载实际安装的产品。

把工坊 EXE 单独复制到其他电脑后无法打开？

工坊自身采用目录分发，必须连同 _internal 一起复制完整 DesktopPackager 文件夹。与此不同，工坊生成给最终用户的 Bundle.exe 内含完整安装载荷，可以单独交付。
